## D12 (approved): Observe-time checks

- **Trusted sources and destinations are separate.** `trusted_sources` answers an origin question (content from here creates no label). A new policy section `destinations` holds named destination classes, each with a `trusted` flag, matched inside Observe on host name or IP/CIDR range. Observe emits only the class name as `destination_class`. A host that matches no class, including every IP-only connection that matches no CIDR, becomes `unknown`.
- **`destination_trusted`** is derived, not emitted: it is true when the event's `destination_class` is a class with `trusted: true`. `unknown` is never trusted. The `fetch` effect uses it (CLAUDE.md C7). C4's `may_connect` entries are destination class names (`package_installer` now lists `package_index`).
- **Threat lists** belong to the Effect question (`effect_threat_list_hit`, weight 4.5). Bloom lookup and exact-list confirmation both run inside Observe; only `threat_list_hit: <list name>` is emitted.
- **Canary URL paths** are matched inside Observe before fingerprinting; only `canary_hit` (a flag) is emitted.
- **`Event` attrs use an allowlist**, not a denylist. The permitted keys are listed in CLAUDE.md C2 and in `EVENT_ATTR_KEYS`; any other key is rejected. Adding a key is a change to both.
- **Sensors pass raw data to Observe in memory** and never hash, log or store it themselves (CLAUDE.md Part A, C2, Phase 8).

Still open under D12: the RawEvent attribute names that carry a host, IP or URL path are not fixed (RawEvent attrs are free-form), so Phase 1 must define them; the allowlist checks keys, not value types; the policy format for threat lists (Bloom file plus exact list) is for Phase 2.

## Structural rules introduced after the first catalog check

These six changes were made on 2026-10-28 **after** catalog check 1 (see [weights-proposal.md](weights-proposal.md)), and they were motivated by what that check showed. The catalog therefore cannot validate them. They are approved, they are fixed from here on, and only held-out variants (Phase 7) can measure them (CLAUDE.md C11, weight methodology).

| # | Change | Motivation (from check 1) |
|---|---|---|
| D13 | **Contract gate.** Block requires a Contract signal or an override; without either, the decision is capped at hold. The verdict records this in `contract_gate`. | Check 1 showed that origin plus one effect of 2.2 nats or more blocked whatever the contract said, with about 49 of 50 such blocks false at a 2 % posterior. |
| D14 | **New signal `effect_response_anomaly_repeated`**, weight 3.5, raised when the Poisson test on repeated anomalies per client is significant. | Repeating the same anomaly added nothing, because only the maximum counts within a question. |
| D15 | **New override: tampering with Refmon itself** (stopping it, altering its policy or binaries) is an immediate block. | Without it a pipeline-tamper story would be capped at hold by D13. |
| D16 | **S26 is split**: S26a non-executable write (benign, allow), S26b outbound connection (block), S26c executable write (block). | One scenario covered three variants with three different outcomes. |
| D17 | **S36**: the print helper is in the document reader's contract (C4 `office`). | Without it the benign story blocked. |
| D18 | **S17-S20** stories carry an initial-access label. Phase 7 keeps a no-label variant of each with expected decision hold. | Single-signal stories were fragile (S20 blocked by 0.005 nats, S19 held). |

Catalog check 2 ([weights-proposal.md](weights-proposal.md)) shows what these rules do: D13 and D14 interact badly for scenarios whose C13 Contract column is "—".

## Structural rules introduced after catalog check 2

Made on 2026-10-28 after catalog check 2 ([weights-proposal.md](weights-proposal.md)), motivated by its findings (eight expected-block scenarios capped at hold by the contract gate, S06 and S17). Approved. As with D13-D18, the catalog cannot validate them, only held-out Phase 7 variants can.

| # | Change | Details |
|---|---|---|
| D19 | **Universal contract** | Four behaviours are forbidden for every role unless the role's own contract explicitly allows them: tampering with security tools or logs, mass change beyond the Poisson threshold, lateral fan-out beyond the Poisson threshold, and repeated response anomalies to one client. A violation is a Contract signal (`contract_universal_violation`, weight 2.0). An allowance removes the Contract signal, and removes the matching Effect only when the story has no external origin label (clarified by D23, below). Without that, S46-S48 would be hold, not allow. New benign scenarios: S46 backup job (`may_mass_change`), S47 admin vulnerability scanner (`may_fan_out`), S48 patch tool stopping services (`may_tamper`). Expected allow. The roles are added in policy. |
| D20 | **Launcher contract** | Starting an executable or script that carries an external origin label (download, removable, mail) and has no valid code signature is a Contract signal (`contract_unsigned_launch`, weight 1.5). `signed` (boolean) joins the attribute allowlist and is determined by the sensor. `signed` is three-valued (true, false, `unknown`) and `unknown` raises no signal (decision after check 3, below). New benign scenario S49: a signed vendor installer from the internet that persists (role `other`, no contract). Expected hold. |
| D21 | **Persistent contract evidence** | A persistent item created by a story with a Contract signal carries that signal (`Label.contract_evidence`, C3 rule 7). When the item runs later, the signal applies to the new story. This is what lets S06 block. |
| D22 | **No-label variants expect block** | The expected decision of the S17 no-label Phase 7 variant changes from hold to block. After check 3 the same was decided for S18, S19 and S20: all four no-label variants now test that the universal contract works without an origin signal. |

Weight rates (fixed before check 3, in [weights-proposal.md](weights-proposal.md)): both Contract weights are conditional on the behaviour having happened, so they add only what the actor's role says beyond the Effect weight for the same behaviour.

## Clarifications made before the freeze (after check 3)

Decided on 2026-10-28 after catalog check 3 and before the freeze. **They clarify rules already in force. None is a new rule or weight**, and none was chosen to move a scenario: check 4 reruns the catalog and every earlier row comes out identical.

| # | Clarification | Details |
|---|---|---|
| D23 | **A contract allowance and the origin label** | An allowance removes the Contract signal always. It removes the matching Effect only when the story carries no external origin label. With a label the behaviour is not ignored and the Effect still counts. New scenario S50: an allowed backup role does mass change in a story with an external origin label. Expected hold (origin 0.8 + effect 2.5 = 3.3 crosses block, but there is no Contract signal, so the gate caps it). The sentence "suppresses the Contract signal and its Effect only when no label" can also be read as voiding the Contract allowance in a labeled story; that reading makes S50 block (L -1.61, sensitivity table in check 4), so the hold expectation fixes the reading used. |
| | **`signed` is three-valued** | `true`, `false` or `unknown`. `unknown` (the sensor cannot check signatures) raises no D20 signal and is never coerced to false. The sensor reports the missing capability in its heartbeat as degraded protection (Phase 6). Replaces my earlier reading that a missing value counts as unsigned. Effect on the catalog: with `unknown`, S32, S33 and S35 are capped at hold instead of block (check 4 sensitivity). |
| | **Principle: missing information never generates evidence** | In CLAUDE.md Part A. A destination class `unknown` is not missing information (the host was seen and matched no class) and still counts for `fetch`. |
| | **S18-S20 no-label variants expect block** | See D22. |
| | **Phase 7 metric** | Every run reports the share of processes classified as role `other`. S49 stays as it is. |
| | **Phase 2 "Done when"** | Contract learning on the benign workloads of S46-S48 must propose the backup, scanner and patch allowances. |
| | **Phase 1 "Done when"** | Fixed an inconsistency I introduced with S49: benign scenarios whose expected decision is hold (S49, S50) have 2 fails, so the "at most 1 fail" clause now excepts them. |
